# Day 38 — Steps 6–7: restrictions and instances

**Goal:** add restrictions to classes, describe one restaurant with the ontology, keep the two in separate files,
and model a fixed list of values (an *enumeration*) as named things instead of text.

## Read

**Step 6: restrictions.** A restriction says what every member of a class has. `burger.ttl` has two:

| Restriction | Reads | OWL words |
|---|---|---|
| on `Fryer` | every fryer has **some** temperature point | `owl:someValuesFrom burger:TemperatureSensor` |
| on `MenuItem` | every menu item has **exactly one** calorie number | `owl:cardinality 1` |

Others you'll see: `owl:allValuesFrom` (*only* this kind), `owl:minCardinality` / `owl:maxCardinality`. Remember
Day 33: under the open world, OWL uses these to *infer*, never to report something missing. A menu item with no
calories doesn't break the restriction to OWL. The shapes on Day 39 check that.

**Step 7: instances.** [`burger_site.ttl`](burger_site.ttl) describes one restaurant: two fryers, a grill, a
walk-in cooler, three sensors and four menu items. Note its *own* namespace, `site:`. The ontology (`burger:`) is
shared by every restaurant; each restaurant's facts live in their own file under their own names. That's the TBox /
ABox split from Day 31, made into two files and two namespaces.

**Enumerations: named things, not text.** How is each menu item cooked? You could write `burger:cookMethod
"fried"`. Text is easy to get wrong: `"fryed"`, `"Fried"`, `"deep-fried"` are all different strings, and nothing
says which are allowed. Instead, give each allowed value its own name. That's an enumeration, and it lives in
[`burger_cook_methods.ttl`](burger_cook_methods.ttl):

```turtle
burger:CookMethodEnumerationValue a owl:Class ; rdfs:subClassOf burger:EnumerationValue .

burger:CookMethod.fried a burger:CookMethodEnumerationValue ;
    rdfs:label "fried" ;
    burger:name "fried" ;
    burger:value "0"^^xsd:nonNegativeInteger ;
    skos:definition "Cooked in hot oil." ;
    burger:needsEquipmentClass burger:Fryer .

burger:cookMethod rdfs:range burger:CookMethodEnumerationValue .   # an IRI, not xsd:string
```

Now an item points at a *thing*: `site:Fries burger:cookMethod burger:CookMethod.fried`. A typo in an IRI is a
different IRI, which a shape (tomorrow) catches. And a named value can carry facts a string can't: a definition, a
number code for the till, the equipment it needs. (The dot in `CookMethod.fried` is just part of the name.)

**Keep names clean.** The name (`"fried"`) and the code (`0`) are separate properties. Don't pack them into one
string like `"0-fried"` or a label like `"15-Fried pickles"`: then every query has to cut the string apart, and the
code can't be checked as a number.

**Same code, different meaning.** Each franchise owner numbers their own specials, so "special 7" is a *Moo melt* at
franchise 101 and a *Spicy stack* at franchise 202 ([`burger_specials.ttl`](burger_specials.ttl)). The code alone is
ambiguous; it resolves only with the franchise ID. The fix is the same idea again: one named thing per
(franchise, code) pair.

These three patterns come from a real ontology: the BACnet ontology generated by
[csml2rdf](https://github.com/JoelBender/csml2rdf/blob/main/bacnet.ttl). Every BACnet enumeration value there is a
named thing (`bacnet:AbortReason.other` with `bacnet:name "other"` and `bacnet:value 0`), and BACnet's
vendor-specific (proprietary) value ranges only mean something together with the vendor's identifier.

[`day38_rdf.py`](day38_rdf.py) lists the restrictions, counts the instances per class, and checks that the
instances only use classes the ontology defines. Then it lists the cook methods, shows each menu item's (finding the
one written as text), finds a label with a code packed in, and resolves "special 7" with and without the franchise.

## How this maps to buildings

> **Buildings box.** **Brick** is one TBox shared by thousands of building models (ABoxes), each in its own
> namespace. **ASHRAE 223P** expresses most "every X has a Y" rules as SHACL shapes rather than OWL restrictions,
> because a building model needs them *checked*, not inferred. **Haystack** works the same way at heart: shared defs
> (the TBox) and per-site records (the ABox).
>
> **Enumerations in building ontologies.** **ASHRAE 223P** does exactly today's pattern: `s223:EnumerationKind` is a
> class tree of named values (`s223:EnumerationKind-DayOfWeek`, media such as `s223:Fluid-Air`), never free text.
> **Brick** uses named things for units (QUDT's `unit:DEG_F`, not the text "°F") but plain strings checked with
> `sh:in` for some value lists. **Haystack** enum tags are strings; the tag's def lists the allowed ones. **BACnet**
> itself is full of enumerations (object types, units, event states), and vendor-proprietary values need the vendor
> ID to mean anything, just like franchise specials.

## Why it matters

Keeping the ontology and the data apart means you can publish one and share it, and load any restaurant (or
building) against it. Named enumeration values do the same for lists of choices: one agreed set of names
that every restaurant's data points at, instead of each kitchen typing its own spelling.
